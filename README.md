# Dev Workspace

A local workspace for reviewing Project Aria recordings, annotating dressing phases and preparing timestamped frames for VLM experiments.

**Available now:** Data Library, MP4 playback, timeline annotation, full-video frame extraction, CSV/JSON annotation export and import, and a single-recording **VLM Run** (sliding-window phase labels through the AIHubMix API) with versioned prompts in **Prompt Library**. Multi-recording VLM Tasks and Evaluation are placeholders for later development. No GPU is required; only VLM Run needs an API key.

Each teammate runs their own local instance. Research recordings, frames, annotations, databases and credentials are not included in the repository.

## 1. Install and start

The verified setup is **macOS with Python 3.12, Node.js 24 and FFmpeg/ffprobe**. The commands and launcher below use a POSIX environment; native Windows startup is not currently supported. Other platforms have not been verified.

Clone the shared repository, or extract a copy of its source code, and run all commands from its root directory:

```sh
git clone git@github.com:CallMeSaltyF1sh/aria-dev-workspace.git
cd aria-dev-workspace
```

On macOS, install the prerequisites through Homebrew. Skip this step if the required tools are already installed:

```sh
brew install python@3.12 ffmpeg fnm
fnm install 24
```

Create a dedicated Python environment and install the locked dependencies:

```sh
python3.12 -m venv app/backend/.venv
app/backend/.venv/bin/python -m pip install -r app/backend/requirements.lock
```

Install the frontend dependencies and start both services:

```sh
fnm exec --using 24 npm ci --prefix app/frontend
python3 scripts/dev_workspace.py
```

Open **<http://127.0.0.1:5173>**. Stop both services with **Ctrl+C** in the terminal that started them. The launcher also runs the backend on `127.0.0.1:8000` and applies SQLite migrations automatically. Use `scripts/dev_workspace.py` as the supported startup entry point.

If Node 24 is installed without fnm, use `npm ci --prefix app/frontend` instead. The launcher uses fnm when it is available, otherwise it uses npm from PATH. If fnm is installed, install Node 24 through it before starting the launcher.

An empty Data Library on first launch is expected: add recordings as described below. `data/` and `workspace/` are created automatically by the backend.

### Optional: VLM API key

VLM Run reads `AIHUBMIX_API_KEY` and `VLM_MODELS` (the models offered in its dropdown; the first is the default) from `.env.local` in the repository root (ignored by Git) when the backend starts:

```sh
cp .env.example .env.local   # then fill in AIHUBMIX_API_KEY
```

Restart the launcher after changing it. In a recording's **VLM Run** tab, choose the garment, step and context, then click **Run VLM**. Each target point is labelled by one request carrying the target frame plus context frames from the 0.1 s frame cache (generated automatically if missing). Results are saved to `workspace/vlm/<asset_id>/<run_id>.json` and shown next to the saved human annotation. Running sends frames to the API and is billed to the key's account.

### Prompt versions

The VLM prompt lives in the repository as `prompts/v1.json`, `prompts/v2.json`, …; `v1` is the prompt ported from the DM2350 pilot. In **Prompt Library**, open a version and choose **New version from …** to edit its context, phase definitions and guidance, with a live preview of the full prompt. The description of the frames and the JSON answer format are fixed, so every version uses the same labels and output. Saving writes a new file and never changes an existing one; **commit the new file** so teammates get it. VLM Run uses the newest version unless you pick one, and each run records the version, its hash and its wording, so results stay comparable.

## 3. Where to put recordings

Use either method:

- Copy **`.mp4` or `.vrs`** files into the repository's `data/` directory, then open Data Library or click **Scan data/**.
- In Data Library, click **Add recordings**, select a destination folder and choose files. The app copies them into `data/`; it does not move the originals from their previous location.

Subdirectories are supported. For example:

```text
data/
├── development/
│   ├── recording_a.mp4
│   └── recording_b.vrs
└── test/
    └── recording_c.mp4
```

Folder names are for organization; participant-level train/development/test separation is a study decision and is not enforced automatically. Use **Metadata** to record the intended dataset split and trial information.

Only source MP4/VRS recordings belong in `data/`. Frames, annotation exports and playback proxies are saved elsewhere. The app rejects symbolic links and paths outside `data/` for managed file operations.

**File operations affect your local files:** confirmed deletion removes the actual source files from `data/`. The app preserves their historical index entries, saved annotations and frame caches, marking the recordings as missing. Scanning files does not generate frames or invoke a model.

## 4. Where generated data is saved

```text
workspace/
├── app.db                                   SQLite index, metadata and job status
├── app.db-wal / app.db-shm                   SQLite runtime files, when present
├── annotations/
│   └── <asset_id>/
│       └── draft.json                       Latest saved human annotation
├── frames/
│   └── <asset_id>/
│       └── <set_id>/
│           ├── frame_000000.jpg
│           ├── frame_000001.jpg
│           └── manifest.json                Source identity and timestamp mappings
├── vlm/
│   └── <asset_id>/
│       └── <run_id>.json                    VLM Run settings, per-target responses, merged phases
└── previews/
    └── <asset_id>/
        └── <source_hash>/
            ├── preview.mp4                  On-demand browser playback proxy
            └── time_mapping.json            VRS proxy's DEVICE_TIME mapping
```

`asset_id` is a local recording ID stored in `app.db`. `set_id` identifies an extraction configuration and source hash; frame caches are not named after the source video's filename.

| Action | Saved result |
| --- | --- |
| Scan or import recordings | Index and metadata in `workspace/app.db`; no frame extraction |
| Edit an annotation | Unsaved changes remain in the browser only |
| Click **Save** in Annotation | `workspace/annotations/<asset_id>/draft.json` |
| Click **Generate frames** | JPEGs and manifest in `workspace/frames/<asset_id>/<set_id>/` |
| Prepare a playback preview | Proxy and, for VRS, time mapping in `workspace/previews/…` |
| Export CSV/JSON | Browser download; choose where to save it |

**Back up `data/` and the entire `workspace/` together.** Stop the app before making a simple file-copy backup. Do not delete `app.db` to reset a view: rescanning identical videos into a new database generates new asset IDs, so existing annotation/cache folders will not automatically reconnect. A single `draft.json` copied to another computer is not sufficient to associate it with a freshly scanned recording.

## 5. First-use workflow

1. Add a recording to `data/` and click **Scan data/**. Click its row to open the detail page.
2. In **Video & Annotation**, play or seek to an interior time, then choose **Add split point**. Editable boundaries snap to 0.1 seconds. Duplicate times do not create duplicate boundaries; video start/end cannot create additional segments.
3. Select `P0`–`P4` or `unclear` for each interval, then click **Save**. Drafts may contain unclassified intervals. Changes are restored from the latest saved draft when reopening a recording; unsaved changes are not written to disk.
4. Open **Frames & QC** and click **Generate frames**. The whole recording is sampled at `0.0, 0.1, 0.2, …` seconds, strictly before its end. Each sample selects the nearest original frame; duplicate selections share one JPEG. The manifest retains requested times, actual times and source indices. Progress is shown, and results are paginated at 24 frames per page.
5. Generate again with the same source/configuration to reuse an intact cache. Source changes are flagged so old results can be reviewed. Generating frames does not submit them to a VLM.

MP4 playback and extraction are verified. VRS requires a usable RGB stream; browser playback uses an on-demand proxy. The VRS adapter and simulated time-mapping tests are implemented, but end-to-end verification with a real Gen 2 VRS recording is still pending. Start with an MP4 when checking a new installation.

## 6. Export annotations for teammates

- **One recording:** save changes, then choose **Annotation → Export → CSV / JSON**.
- **All annotated recordings:** choose **Data Library → Export annotations → CSV / JSON**. This includes all folders, independent of the current filters or selection.
- Only saved drafts with at least one valid phase label are included. Partially labeled recordings retain their unclassified intervals: JSON uses `null`; CSV leaves the phase blank. The preview shows recording, interval and unclassified counts.
- Exports include relative video identifiers, source hashes, timing and annotation versions, allowing teammates to identify the matching source recordings. Changed/missing sources are flagged. They do not include video, frames, study metadata or absolute machine paths; exported filenames/content are not automatically anonymized.

Downloads go to the browser's configured download location or a location chosen in its save dialog. The app does **not** automatically write exports into the project. If saving inside the project, use `exports/`; that directory and generated `annotations_*.csv`/`annotations_*.json` filenames are ignored by Git.

Source recordings and exported labels are shared separately from Git. Copying an export into `data/` does not import it; use **Data Library → Import annotations** instead (below). The older pilot CSV migration utility is documented in [app/README.md](app/README.md).

### Import annotations from teammates

Choose **Data Library → Import annotations** and select a CSV or JSON file produced by Export annotations. Each record is matched to a recording in your `data/` by its source hash, so the video must be the same file but may have another name or folder. A preview lists every record before anything is written:

| Result | Meaning |
| --- | --- |
| Will import | The recording has no saved annotation yet; it is imported. |
| Differs from local | You already saved a different annotation. It is kept unless you tick **Overwrite**. |
| Already the same | Nothing to do. |
| No matching video | No local recording has this content. Add the video to `data/` and scan. |
| Ambiguous | Several identical copies exist and none has the exported filename. |
| Invalid | Duration, labels or intervals do not match the local recording. |

Imported annotations are saved as new local revisions. If annotations change between preview and import, the import is refused and must be previewed again.

## 7. Build without the frontend development server

After installing dependencies:

```sh
fnm exec --using 24 npm run build --prefix app/frontend
python3 scripts/dev_workspace.py --production
```

Open **<http://127.0.0.1:8000>**. Stop the development services first if port 8000 is occupied. Rebuild the frontend and restart the server after changing the source.

## 8. Common setup issues

| Symptom | Check |
| --- | --- |
| No recordings appear | Put MP4/VRS files under this checkout's `data/`, then scan. Check folder/search filters. |
| `ffmpeg` / `ffprobe` is missing | Install FFmpeg and ensure both commands are on PATH. |
| Backend environment is missing | Create `app/backend/.venv` using Python 3.12 and install `requirements.lock`. |
| fnm cannot find Node 24 | Run `fnm install 24`. |
| Port 5173 or 8000 is already in use | Use the already-running instance, or stop its original terminal with Ctrl+C before restarting. |
| Aria dependency installation fails | Check Python is 3.12 and use a supported platform with a matching Project Aria Tools wheel; another Python version may not have a compatible wheel. |
| A recording cannot play | Read its media error; try **Prepare preview** if available. VRS cannot play directly in the browser. |
| Annotation export is disabled | Save edits first. A draft without any phase labels is not an annotated recording for export. |

The backend health endpoint is <http://127.0.0.1:8000/api/health>. It should report `status: "ok"`, `ffmpeg: true` and `ffprobe: true`.
